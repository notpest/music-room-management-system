================================================================================
MUSIC ROOM MANAGEMENT SYSTEM - COMPLETE ARCHITECTURAL & CODEBASE REPORT
================================================================================
Date of Analysis: June 19, 2026
Project Stack: Next.js 15 (TypeScript, TailwindCSS), Sequelize ORM, PostgreSQL (Supabase), Python (Gmail Integration)

This report provides a full breakdown of the codebase, covering features, architecture, optimizations, critical flaws, logic flow, and deployment details.

--------------------------------------------------------------------------------
1. CORE FEATURES
--------------------------------------------------------------------------------
* Room Booking & Request System: Allows musical bands and profiles to submit requests for specific room slots. Requests go through an approval workflow (pending, approved, denied).
* Automated Slot Scheduling: Upon request approval, a hard slot reservation is automatically generated and marked as 'booked'. 
* Slot Configuration Management: Admin panel features to configure standard predefined time intervals (slots) that users can choose from.
* Equipment Tracking & Audit Logs: Tracks musical instruments and equipment usage via an entry logging system. Includes automated scan integrations.
* Band Affiliation Mapping: Supports multi-member configurations through a many-to-many relationship mapping Users to Bands (`UserBand`). Bookings are categorized per Band profile.
* Session Audit History: Logs user login and logout history events dynamically (`LoginHistory`).
* High-Fidelity Interactive UI: Integrates advanced custom visuals using Framer Motion animations, Three.js/React Three Fiber 3D elements, and stylized dashboard views.

--------------------------------------------------------------------------------
2. SYSTEM ARCHITECTURE
--------------------------------------------------------------------------------
The project uses a hybrid, multi-paradigm structure:
* Frontend (App Router): The presentation layer lives under the Next.js 15 App router (`app/`). It leverages Client Components (`"use client"`) heavily, effectively creating a rich single-page-app experience within Next.js.
* Backend / API Layer (Dual Paradigm): 
  - Authentication and registration endpoints are built using Next.js App Router API format (`app/api/auth/`).
  - Standard resource APIs (Rooms, Slots, Requests, Entry Logs) are built using the older Next.js Pages router format (`pages/api/`).
* Database & Object-Relational Mapping (ORM): PostgreSQL database hosted on Supabase, abstracted via Sequelize ORM.
* Background Automation Worker: A Python-based script (`parse_gmail.py`) handling Google Gmail API integration to process scanning data.

--------------------------------------------------------------------------------
3. APPLICATION LOGIC & DATA FLOWS
--------------------------------------------------------------------------------
* Authentication Flow: NextAuth handles identity management using a standard Credentials provider. Passwords are securely hashed/compared via `bcryptjs`. The JWT and session callbacks are customized to inject the user's role and primary `band_id` right into the client context.
* Login Auditing Flow: NextAuth's event listeners (`events.signIn` and `events.signOut`) act as hooks to automatically create or update timestamps in the `LoginHistory` table when session states change.
* Booking Workflow: 
  1. A user submits a POST request to `/api/requests` providing their band, slot timings, and a room UUID.
  2. The backend validates against overlapping *pending* requests for that same band and room to prevent double-submitting.
  3. An admin updates the request status via a PUT call.
  4. If status transitions to 'approved', a conflict check validates against already *booked* slots. If clear, a new `Slot` row is inserted, and the request is bound to it via `slot_id`.
  5. If an approved request is canceled or denied later, the bound slot is automatically purged from the table.
* Gmail Scan Integration: 
  1. Barcode/QR scanners or IoT entry points send an email with an equipment UUID to a dedicated mailbox.
  2. When an admin fires a POST request to `/api/entrylogs`, the Next.js server spawns a child process executing `python parse_gmail.py`.
  3. The Python script logs into Gmail via OAuth2 (using `credentials.json` and `token.pickle`), retrieves unread inbox items, extracts the equipment UUID via regex, updates the `entry_log` database table directly via `psycopg2`, and marks the emails as read.

--------------------------------------------------------------------------------
4. DESIGN CRITICAL FLAWS & VULNERABILITIES
--------------------------------------------------------------------------------
* CRITICAL SECURITY ISSUE (Hardcoded Credentials): `parse_gmail.py` contains plaintext production database credentials (Host, User, Password, Port). This exposes the production Supabase PostgreSQL instance to anyone with read rights to the codebase. These should be fetched from environment variables.
* PERFORMANCE BOTTLENECK (N+1 Queries): In `pages/api/requests.ts` (GET handler), the script fetches all requests, then loops through them using `Promise.all(requests.map(async ...))`, performing distinct `User.findOne`, `UserBand.findOne`, and `Band.findOne` database lookups for *every single item*. This completely bypasses SQL joins (`include` syntax in Sequelize) and will degrade exponentially as the database grows.
* ARCHITECTURAL PARADIGM SPLIT: Splitting the API routes between the App Router (`app/api/`) and Pages Router (`pages/api/`) creates an inconsistent server architecture, increasing maintainability overhead and complicating request handling conventions.
* SERVERLESS DEPLOYMENT INCOMPATIBILITY: The entry log execution path calls `exec("python parse_gmail.py")` inside a Node environment. This makes the project entirely incompatible with standard Next.js serverless platforms (like Vercel or Netlify) because serverless functions do not bundle full Python runtimes out-of-the-box and operate on a read-only filesystem, which breaks the script's `token.pickle` write operations.
* INCOMPLETE MODEL INITIALIZATION INDEX: `models/initmodels.ts` only imports `User`, `Band`, and `UserBand`. Sibling models (such as `Room`, `Slot`, `Request`, `EntryLog`) rely on side-effects from being imported elsewhere during code execution to run their `.init()` blocks and attach their relationships. If a feature references an un-imported model relationship early in the lifecycle, it will crash.
* EXTREME UI DEPENDENCY BLOAT: The project imports four heavy UI/Design systems: `@chakra-ui/react`, `@heroui/react`, `@nextui-org/react`, and `@mui/material`. This leads to massive client bundle sizes, redundant CSS rule declarations, and high risk of style/theme pollution.

--------------------------------------------------------------------------------
5. OPTIMIZATIONS FOUND IN CODEBASE
--------------------------------------------------------------------------------
* Dynamic Component Loading: The `Navbar` component is loaded using `next/dynamic` with `ssr: false`. This avoids hydration mismatches common with client-only context state (like NextAuth session checks) and enhances initial layout execution.
* Database Connection Pooling: The Sequelize connection (`database.ts`) is configured with an active pool (`max: 10`, `idle: 10000`, `acquire: 30000`). This ensures reuse of socket connections and limits database fatigue under load.

--------------------------------------------------------------------------------
6. DEPLOYMENT & INFRASTRUCTURE DETAILS
--------------------------------------------------------------------------------
* Infrastructure Requirements: Due to the tight pairing between Node.js and a localized Python environment via `child_process.exec`, this application must be deployed onto a full virtual machine (VPS like AWS EC2, DigitalOcean Droplet, Linode) or custom multi-buildpack Docker containers rather than serverless architectures.
* External Dependencies:
  - Database: PostgreSQL cluster hosted on Supabase (currently provisioned in the AWS `ap-south-1` region).
  - Mail Authentication: Local Google API files `credentials.json` and `token.pickle` must reside in the project's root folder to maintain the Gmail scraping routine.
* Required Environment Variables:
  - `DATABASE_URL`: Connection string for Sequelize.
  - `NEXTAUTH_SECRET`: Secret string for encrypting NextAuth JWTs.
